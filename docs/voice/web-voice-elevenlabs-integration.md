# Web Voice + ElevenLabs Integration

The complete production Agent prompt is maintained only in [ElevenLabs System Prompt](./elevenlabs-system-prompt.md). This document covers integration architecture and operations; it is not an alternate source of prompt rules.

## Architecture

The browser voice channel starts through this trust path:

```text
Browser
  -> publicWidgetKey
  -> POST /api/v1/voice/web/session
  -> WebVoiceChannel resolution
  -> trusted Tenant + optional Location
  -> ElevenLabs signed URL generated by the backend
  -> temporary signed URL returned to the frontend
  -> microphone permission
  -> ElevenLabs React SDK
  -> live conversation
```

`publicWidgetKey` is an opaque public routing identifier, not a secret. The browser sends only `{ "widgetKey": "wgt_..." }`. The backend validates its format, resolves an active `WebVoiceChannel`, and derives the tenant and optional location from that record. Browser-supplied `tenantId` or `locationId` values are neither accepted nor trusted.

`ELEVENLABS_API_KEY` remains backend-only and is used only when the backend requests a signed conversation URL. `VOICE_GATEWAY_API_KEY` belongs to the separate service-to-service voice gateway and must not be exposed to the browser. The frontend contains only `NEXT_PUBLIC_API_BASE_URL` and `NEXT_PUBLIC_VOICE_WIDGET_KEY`; their `NEXT_PUBLIC_` prefix intentionally makes them browser-visible.

The web-session endpoint is intentionally public. It does not require a clinic JWT, refresh-token recovery, `X-Tenant-Id`, `TenantMembership`, or `VOICE_GATEWAY_API_KEY`. The dedicated `publicApiRequest` path omits credentials and authorization behavior, preventing an anonymous widget call from becoming coupled to the clinic application's authenticated API lifecycle.

## Signed URL lifecycle

A signed URL is requested only after the user clicks **Start a Call** and grants microphone permission. It is not requested on page load. The temporary URL is validated and passed immediately to ElevenLabs; it is not placed in local or session storage, cached, rendered, or logged. Every new conversation gets a fresh URL. A retry caused by an expired or rejected startup credential also fetches a new URL once.

The URL's expiry controls conversation initiation. It is not a conversation-duration limit: once ElevenLabs has established the conversation, the initiation expiry does not end that active call.

## Microphone permission

The click handler explicitly calls `navigator.mediaDevices.getUserMedia({ audio: true })` before fetching the signed session and starting ElevenLabs. Keeping this request in the user gesture path satisfies browser media-permission policies and gives the UI a clean failure point for denial or an unavailable media API.

After permission succeeds, the code immediately stops every track on the temporary stream. The stream is only a permission probe; the ElevenLabs SDK manages the live call media. `localhost` is accepted as a secure context for local development. Production must use HTTPS. Permission denial and missing media APIs map to safe user-facing errors rather than exposing browser exceptions.

## ElevenLabs SDK and startup

The installed dependency tree currently resolves to:

- `@elevenlabs/react` 1.15.0
- `@elevenlabs/client` 1.23.0

`WebVoiceCard` provides `ConversationProvider` and uses `useConversationControls`, `useConversationStatus`, and `useConversationMode`. Its working startup options are:

```ts
startSession({
  signedUrl: session.signedUrl,
  connectionType: "websocket",
  textOnly: false,
  dynamicVariables: {
    secret__voice_widget_key: widgetKey,
  },
  // lifecycle callbacks
});
```

The installed SDK's `BaseSessionConfig` supports `dynamicVariables` as string, number, or boolean values. The runtime widget key is supplied for direct substitution into the FAQ webhook header; it is not an LLM-generated tool argument. No tenant or location database ID is sent as a dynamic variable.

The backend currently produces an ElevenLabs signed conversation URL, so this implementation explicitly selects WebSocket. This is an implementation choice, not a permanent claim that WebSocket is the only supported architecture. A deliberate future WebRTC migration must adopt the appropriate ElevenLabs token/authentication flow instead of blindly reusing this signed-URL path.

## Async control flow

Startup proceeds as follows:

1. The user clicks **Start a Call**.
2. The card guards against duplicate operations, enters `CONNECTING`, and clears stale error/context state.
3. It requests microphone permission and stops the temporary permission stream.
4. It calls `createWebVoiceSession(widgetKey)` to request a fresh session.
5. The caller awaits the API promise; the API function awaits `publicApiRequest`, validates the response with Zod, and returns the validated result.
6. The caller verifies that `signedUrl` is a non-empty string.
7. It starts the 12-second connection timer and calls ElevenLabs `startSession` with the signed URL, explicit WebSocket transport, and audio enabled.
8. SDK callbacks and `useConversationStatus` report real connection state.
9. `onConnect` clears the timer and moves the UI to `CONNECTED`.
10. **End Call** invalidates the startup attempt, calls `endSession`, and clears context and errors. Unexpected disconnects instead map to `IDLE` or `ERROR` according to the SDK reason.

The implementation bug found during development was an async result-propagation failure: the HTTP/API function could complete successfully while an intermediate async or mutation wrapper did not return its result to the caller. The caller therefore never resumed with the session and the UI remained in `CONNECTING` despite HTTP 200.

The working path no longer uses a TanStack mutation for voice startup. It directly awaits `createWebVoiceSession`, which directly returns the validated session. The maintenance rule is broader: every async layer must `return` or `await` the session result correctly. If a mutation is introduced later, use its awaitable `mutateAsync` path (and return that promise), not fire-and-forget `mutate`, when subsequent startup steps depend on the returned signed URL.

## Connection states and timeout

The UI state machine contains `IDLE`, `CONNECTING`, `CONNECTED`, `DISCONNECTING`, and `ERROR`. The installed ElevenLabs integration reports `disconnected`, `connecting`, `connected`, and `error`. The displayed state incorporates SDK `connected` and startup `error` status, while lifecycle callbacks perform the definitive transitions and cleanup. UI state must follow actual SDK status/callbacks and must never remain indefinitely in `CONNECTING`.

After the signed response is validated, a 12-second startup timer covers the ElevenLabs connection phase. It protects against a missing connection callback; it is not a call-duration limit. On expiry, the code ends the pending SDK session and enters a safe error state. The session API independently has a 12-second abort timeout. Neither timer should intercept or discard a result that has already completed its respective phase.

## Error handling and safe diagnostics

The UI maps microphone denial, unavailable media APIs, an API timeout, invalid/unavailable widget keys (404), rate limiting (429), provider failures (502/503), malformed responses, SDK startup failures, unexpected disconnects, and connection timeout to bounded messages suitable for end users. Zod rejects malformed successful API responses before the SDK sees them. The backend rate-limits the public endpoint and converts provider failures to safe gateway errors.

Development diagnostics retain only useful lifecycle markers and safe status/disconnect metadata. Raw signed URLs, full widget keys, API keys, auth headers, tokens, provider error payloads, and protected health information (PHI) must never appear in browser or backend logs. Error logging redacts URL- and credential-shaped text before writing it.

## Security boundary and future phone channel

```text
WEB CHANNEL                         PHONE CHANNEL — future
publicWidgetKey                     calledNumber
  -> WebVoiceChannel                  -> TelephonyNumber
  -> VoiceContext                     -> VoiceContext
                     \               /
                      shared business tools
```

Everything after `VoiceContext` should be shared. Business tools must consume that trusted, server-resolved context and must never authorize or route work using tenant identifiers supplied by the browser, caller, prompt, or language model.

After conversation startup, the FAQ tool follows a second trust-resolution path:

```text
WEB_WIDGET
  -> runtime widget context
  -> ElevenLabs webhook tool
  -> Voice Gateway machine authentication
  -> widgetKey re-resolution
  -> trusted VoiceContext
  -> VoiceFaqService
```

Every machine tool request re-establishes context. The language model owns only the concise FAQ `query`; it never owns tenant/location routing. See [ElevenLabs FAQ webhook tool](./elevenlabs-faq-tool.md) for dashboard configuration and verification. A short-lived signed context/session token may augment this stateless re-resolution later when complex call state exists; no `CallSession`, Redis state, or context JWT is introduced at this stage.

For FAQ calls, ElevenLabs transports conversation `selected_location_key` in the dynamic `X-Voice-Selected-Location-Key` header. The backend first trusts only the tenant re-established from `X-Voice-Widget-Key`, then accepts the selected `locationNumber` only when it belongs to that tenant and is `ACTIVE`. A valid selected location overrides the WebVoiceChannel/default location; missing or blank selection uses that default; no effective location limits results to tenant-wide FAQs. Saving Agent configuration is not enough: publish changes before testing live application sessions. The complete manual prompt publishing workflow is documented in the canonical [ElevenLabs System Prompt](./elevenlabs-system-prompt.md).

## Troubleshooting

For a focused development investigation, instrument or follow this sequence without logging secrets:

```text
voice:start-clicked
voice:requesting-microphone
voice:microphone-granted
voice:requesting-session
voice:session-api-enter
voice:session-http-start
voice:session-http-resolved
voice:session-body-read
voice:session-response-validated
voice:session-api-return
voice:caller-after-session-await
voice:signed-session-received
voice:calling-startSession
voice:startSession-resolved
voice:onConnect
voice:status connected
```

The production code need not retain every temporary trace; add them locally at the corresponding boundaries when diagnosis requires them. Interpret the last reached boundary:

- Before `microphone-granted`: browser permission, device availability, or secure-context issue.
- After `requesting-session`: frontend public API/session path; add the API and HTTP boundary markers to narrow it further.
- API returns but the caller never reaches `caller-after-session-await`: missing async return/await or mutation-result propagation.
- `calling-startSession` is reached but connection never follows: ElevenLabs SDK, WebSocket transport, network, or provider layer.
- Startup reaches neither success nor an error callback: confirm the 12-second timer exits `CONNECTING` and that attempt/unmount guards have not invalidated the callback.
